[Finding 1] [High] Native bitmap processing ignores row stride
Files:
  - android/app/src/main/cpp/matting_jni.cpp (lines 165-170, 291-308, 351-356, 430-445)
  - android/app/src/main/cpp/rife_jni.cpp (lines 167-176, 210-217)
  - android/app/src/main/cpp/pii_ncnn_jni.cpp (lines 182-187, 271-276)
Verification:
  - In matting_jni.cpp, input bitmap pixel buffer is passed directly to `ncnn::Mat::from_pixels_resize` without passing `info.stride`. On output mask generation, pixels are written via `rgba_out[i * 4 + c]` assuming `i = 0..src_w * src_h` without taking destination bitmap row stride (`mask_info.stride`) into account.
  - In rife_jni.cpp, pixels from `bitmap0` and `bitmap1` are packed into `g_rgb0` and `g_rgb1` using `i * 4` flat indexing without `info0.stride` or `info1.stride`. On output, `p_out[i * 4 + c]` is written without considering `out_info.stride`.
  - In pii_ncnn_jni.cpp, face detection and YOLO PII detection both call `from_pixels_resize(reinterpret_cast<const unsigned char*>(pixels), ncnn::Mat::PIXEL_RGBA2RGB, orig_w, orig_h, ...)` without passing `info.stride`.
Consequence: On Android devices where hardware bitmap buffers contain row padding (stride > width * 4), native code reads skewed/shifted color channels, corrupts mask boundaries, and produces skewed video frames and incorrect object detections.

[Finding 2] [High] RIFE can leave the first bitmap locked
File:
  - android/app/src/main/cpp/rife_jni.cpp (lines 152-155)
Verification:
  - The locking code is written as:
      if (AndroidBitmap_lockPixels(env, bitmap0, &pixels0) != ANDROID_BITMAP_RESULT_SUCCESS ||
          AndroidBitmap_lockPixels(env, bitmap1, &pixels1) != ANDROID_BITMAP_RESULT_SUCCESS) {
          return nullptr;
      }
  - If `lockPixels(env, bitmap0, &pixels0)` succeeds, but `lockPixels(env, bitmap1, &pixels1)` fails, the `||` short-circuits and immediately returns `nullptr` without ever calling `AndroidBitmap_unlockPixels(env, bitmap0)`.
Consequence: Leaves `bitmap0` in a permanently locked state, violating AndroidBitmap NDK lifecycle invariants, leading to graphics buffer corruption or crashes on subsequent operations.

[Finding 3] [High] Face detection ignores NCNN extraction errors before indexing outputs
File:
  - android/app/src/main/cpp/pii_ncnn_jni.cpp (lines 198-224)
Verification:
  - Lines 199-200 call:
      ex.extract("scores", scores);
      ex.extract("boxes", boxes);
    Neither return code (`int`) is checked.
  - Immediately following, lines 207-213 iterate over all priors:
      float score = scores.channel(0)[i * 2 + 1];
      float x_center = boxes.channel(0)[i * 4] * center_variance * g_ultra_priors[i][2] + g_ultra_priors[i][0];
    There is zero verification that `scores` or `boxes` are non-empty, nor that their channel dimensions/element counts can safely accommodate `num_anchors * 2` and `num_anchors * 4`.
Consequence: If inference fails or tensor dimensions mismatch, the native runtime dereferences invalid or unallocated memory, causing a native SIGSEGV crash.

[Finding 4] [High] RIFE continues after failed GPU inference operations
File:
  - android/app/src/main/cpp/rife/rife.cpp (lines 562, 573, 599, 610, 715, 742, 4264, 4287, 4342, 4355, 4366, etc.)
Verification:
  - Throughout `RIFE::process` (both Vulkan GPU and CPU paths), calls to `ex.extract(...)` ignore the return value.
  - When Vulkan allocation or shader dispatch fails, the subsequent pipeline operations (warp forward, blending, temporal averaging) continue executing against empty or invalid VkMat tensors.
Consequence: GPU errors cause downstream pipeline panics, visual artifact corruptions, or device driver timeouts instead of cleanly surfacing an error code to the caller.

[Finding 5] [Medium–High] YOLO PII inference has an unchecked fallback extraction
File:
  - android/app/src/main/cpp/pii_ncnn_jni.cpp (lines 286-292)
Verification:
  - Lines 287-291:
      int ret = ex.extract("out0", out);
      if (ret != 0) {
          ex.extract("output", out);
      }
    The return value of the fallback extraction `ex.extract("output", out)` is completely unchecked.
Consequence: When both extractions fail, the fallback return code is discarded and no error is reported; while `out.empty()` check protects decoding, the failure is masked and not reported to the caller.

[Finding 6] [High] Target-size compression deletes its own fallback file
File:
  - android/app/src/main/java/com/veilframe/app/pdf/operations/PdfCompressor.kt (lines 278-303)
Verification:
  - When binary search iterations cannot achieve `targetSizeBytes`, it yields:
      TargetSizeNotReachedException(fallbackFile = bestFile, ...)
  - In the `finally` block:
      cacheDir.listFiles()?.forEach { file ->
          if (file.name.startsWith("iter_") || file.name.startsWith("temp_target_compress_")) {

    `bestFile` was created with prefix `iter_` during the search.
Consequence: The `finally` block deletes `bestFile` before the caller catches the exception and accesses `e.fallbackFile`. The fallback file no longer exists on disk when the caller tries to copy or use it.

[Finding 7] [Medium–High] Target-size compression swallows coroutine cancellation
File:
  - android/app/src/main/java/com/veilframe/app/pdf/operations/PdfCompressor.kt (lines 293-295)
Verification:
  - In `compressPdfToTargetSizeStrict`:
      } catch (e: Exception) {

      }
    Unlike `compressPdf()` which explicitly catches `CancellationException` and re-throws it (`catch (e: CancellationException) { throw e }`), this catch-all swallows cancellation, converting it into a standard `Result.failure`.
Consequence: Breaks structured coroutine cancellation when the user navigates away or cancels the job, keeping parent jobs or UI states confused.

[Finding 8] [High] PDF flattening can report success without saving the new PDF
File:
  - android/app/src/main/java/com/veilframe/app/pdf/operations/PdfFlattener.kt (lines 150-171)
Verification:
  - In `flattenPdf`:
      context.contentResolver.openOutputStream(outputUri)?.use { outputStream ->
          document.save(outputStream)

      }
    If `openOutputStream(outputUri)` returns null, saving is skipped silently without exception.
  - The code then tests:

Consequence: If the destination stream cannot be opened for writing, the operation falsely reports `success = true`, masking failure and leaving the caller with an un-flattened or stale document.

[Finding 9] [Medium] The "remove JavaScript" option also removes legitimate PDF open actions

[Finding 10] [Medium] Form-flattening count is calculated after the fields are flattened

[Finding 11] [Medium] Text extraction does not explicitly close its input stream

Step 1: Stride-Aware Native Bitmap Access (Finding 1)
------------------------------------------------------------------
- `matting_jni.cpp`:
  - Input: Read `info.stride` (bytes per row). Call `ncnn::Mat::from_pixels_resize(pixels, ncnn::Mat::PIXEL_RGBA2RGB, src_w, src_h, static_cast<int>(info.stride), scaled_w, scaled_h)`.
  - Output: Query `mask_info.stride`. In the pixel write loop, calculate row pointers using `y * mask_info.stride + x * 4` instead of flat `(y * src_w + x) * 4`.
  - Apply to both `nativeProcess` and `nativeProcessLegacy`.
- `rife_jni.cpp`:
  - Input: Query `info0.stride` and `info1.stride`. Copy pixels row-by-row:
    `const unsigned char* row0 = p0 + y * info0.stride;`
    `const unsigned char* row1 = p1 + y * info1.stride;`
    `unsigned char* dst0 = d0 + y * w * 3;`
    `unsigned char* dst1 = d1 + y * w * 3;`
  - Output: Query `out_info.stride`. Write output RGB to RGBA row-by-row:
    `unsigned char* row_out = p_out + y * out_info.stride;`
    `const unsigned char* src_rgb = rgb_out + y * w * 3;`
- `pii_ncnn_jni.cpp`:
  - Query `info.stride`. Pass `static_cast<int>(info.stride)` to `from_pixels_resize` for both `nativeDetectFaces` and `nativeDetectPii`.

Step 2: Safe Scoped Bitmap Lock Lifecycle in RIFE (Finding 2)

- Then lock `bitmap1`. If `lockPixels(env, bitmap1, &pixels1) != ANDROID_BITMAP_RESULT_SUCCESS`:
  - Immediately unlock `bitmap0` before returning `nullptr`.
- Implement RAII guard `BitmapLockGuard` or explicit clean unlock on all return paths.
