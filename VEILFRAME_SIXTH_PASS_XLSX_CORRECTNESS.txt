### 2\. Critical findings

### Finding 1 — Oversized columns can exceed the PDF page limit

High severity

In `SpreadsheetLayoutEngine.kt`, `partitionColumns()` contains this logic:

```kotlin
if (activeCols.isEmpty() || groupWidth + nextW <= baseAvail) {
    activeCols.add(colIdx)
    groupWidth += nextW
    colIdx++
}
```

The first column is accepted even if its width exceeds the available tile width.

The resulting page width is then calculated as:

```kotlin
val tileWidth = maxOf(
    limits.minPageWidth,
    groupTotalTableWidth + (2 * limits.margin)
)
```

There is no upper-bound validation here.

Why this matters: If one column is 20,000 pt wide, the planner creates a page wider than 14,400 pt rather than splitting that column's content or safely handling it through another strategy.

This directly conflicts with the report's claim that extremely wide individual cells are handled cleanly.

The current test uses a roughly 300-character string and checks that the page is wider than 1,200 pt. It does not test a column wider than 14,400 pt.

Required correction: Introduce a separate oversized-column policy. Either:

* Split the cell's content into contiguous horizontal fragments while preserving its identity and reading order; or

* Use an explicitly supported extended-size page strategy.

Do not silently generate a page that exceeds the selected PDF coordinate limit.

### Finding 2 — Oversized rows can exceed the tile height limit

High severity

`partitionRows()` has the equivalent problem:

```kotlin
if (rIdx == startRow || groupHeight + nextH <= availHeight) {
    groupHeight += nextH
    rIdx++
}
```

The first row is accepted even if its height exceeds the available tile height.

The tile height then becomes:

```kotlin
maxOf(
    limits.minPageHeight,
    limits.headerHeight + groupHeight +
        (2 * limits.margin) + (limits.bannerHeight * 2)
)
```

Again, there is no upper-bound validation.

Why this matters: A single row with an enormous multiline cell can create an oversized tile page. The existing row chunking logic in the natural renderer does not solve this problem in the tiled renderer.

Required correction: Split oversized rows into vertical fragments, with continuation metadata. The fragments must preserve line order and must not duplicate or omit text.

### Finding 3 — The merged-cell implementation does not preserve merged geometry

High severity

The parser correctly reads `<mergeCell>` references into `CellRangeAddress`.

However, the rendering code only uses the merged range to decide whether text should be drawn:

```kotlin
val merged = layout.mergedRegions.firstOrNull {
    it.contains(rIdx, colIndex)
}

val shouldDrawText = if (merged != null) {
    rIdx == merged.firstRow &&
        colIndex == merged.firstCol
} else {
    true
}
```

This suppresses text in non-anchor cells. It does not actually combine their dimensions.

The renderer still calls `drawCellChunk()` with the individual cell's original width and height.

For a merged range such as `A1:F2`, the renderer should account for the entire merged rectangle:

* Combined width of columns A–F.

* Combined height of rows 1–2.

* Correct border treatment around the outer boundary.

* Anchor text positioned and wrapped within that combined rectangle.

The present implementation does not establish that behavior.

There is also a tile-boundary problem: the anchor cell may be on one tile while the remainder of its merged range is on another. Suppressing text in non-anchor cells does not itself create a correct continuation representation.

Required correction: Add merged-region-aware geometry and a tile-intersection model. Test horizontal, vertical, and two-dimensional merges crossing tile boundaries.

### Finding 4 — The cell-integrity test does not verify ordering

High severity

The test `testXlsxTiledContentIntegrityCellIdExactMatchNoDuplicatesNoLoss` creates:

```kotlin
val expectedList = mutableListOf<String>()
```

It populates that list in row-major order, but never compares it with the extracted sequence.

Instead, the test checks:

* Expected token count equals extracted token count.

* Expected set equals extracted set.

* No token appears more than once.

Those are useful checks, but they do not prove ordering.

For example, a PDF containing all 300 tokens in reverse order could pass those assertions.

Required correction:

```kotlin
assertEquals(expectedList, extractedMatches)
```

However, that comparison must account for how the PDF text extractor orders text across pages. For tiled output, the test should explicitly validate page sequence, row-group sequence, column-group sequence, and cell order within each tile.

This is particularly important because row-major panel ordering is one of your central design requirements.

### 3\. Additional findings

### Finding 5 — Frozen columns work, but their test is weak

Medium severity

The planner does correctly maintain a list of frozen columns and includes them in subsequent horizontal panels.

However, the test only checks that `EMP_KEY_1` appears on page 2. It does not establish:

* That the column is drawn at the correct position.

* That it appears exactly once per panel.

* That the other columns remain in their original sequence.

* That repeated columns do not cause width overflow.

* That repetition works across multiple vertical row groups.

Also, `frozenColumnsCount` is currently hardcoded to `1` in `buildSheetLayout()`. It does not read actual XLSX frozen-pane metadata.

So this is currently repeat-first-column functionality, not full Excel frozen-pane support.

### Finding 6 — Extended-size rendering is logically consistent, but viewer compatibility remains unproven

Source implementation verified

The implementation does the following:

```kotlin
val pageBounds = PDRectangle(
    plan.pageWidth,
    plan.pageHeight
)

currentPage.setUserUnit(plan.userUnit)

contentStream.transform(
    Matrix.getScaleInstance(
        1f / plan.userUnit,
        1f / plan.userUnit
    )
)
```

The planner reduces the page's coordinate dimensions, applies `/UserUnit`, and transforms the content stream so that the intended physical dimensions and font sizes are retained.

That approach is internally consistent.

There is an important distinction, though:

* The PDFBox source implementation exists.

* The tests check `page.userUnit` and MediaBox dimensions.

* Neither of those proves that external PDF readers render the page correctly.

The report claims emulator verification, but it does not establish compatibility across independent PDF viewers.

I would test at least Android `PdfRenderer`, Adobe Acrobat Reader, and one additional Android PDF viewer using the same generated extended-size file.

### Finding 7 — The test suite does not prove 200 × 2,000 cell preservation

Medium severity

The report's requested stress test was 200 columns × 2,000 rows.

The actual integrity test I inspected uses:

```kotlin
val colCount = 15
val rowCount = 20
```

That is 300 cells.

The separate 200-column × 100-row test checks a few sample tokens, not every cell.

Therefore, the architecture has not yet demonstrated the full 200 × 2,000 integrity requirement.

### Finding 8 — Empty sheets and sparse rows need more coverage

The parser materializes supported row gaps, but it rejects gaps greater than 500. That is preferable to silently shifting data.

However, the parser also trims trailing empty rows, and the layout engine uses the resulting dense row representation. The `sparseRows` representation is not used by the layout engine.

This means large sparse worksheets still have a potentially expensive dense representation, and their original row coordinates need more careful testing.

I would add tests for:

* A sheet with only one populated cell at a high row and column.

* Trailing empty rows and columns.

* Empty sheets mixed with populated sheets.

* Large sparse ranges.

* A merged region extending beyond the final populated row.

SECTION 2: EXHAUSTIVE REQUIREMENT MAPPING AND GAP ANALYSIS

1. TILE WIDTH & HEIGHT STRICT CEILING ENFORCEMENT (P0):
   - Current Defect: In partitionColumns() and partitionRows(), when an individual column or row exceeds available tile space, the planner accepted it unconditionally without capping page bounds. If a column was 20,000 pt wide or a row was 20,000 pt tall, tileWidth/tileHeight exceeded 14,400 pt.
   - Requirement:
     * In buildSheetLayout(): Individual column width must be bounded by available table budget (`limits.maxStandardCoord - 2 * limits.margin`). If an unbroken word/line is wider, wrap/chunk it to fit within available width. If maxTileWidthOverride is active, column width cannot exceed `maxTileWidthOverride - 2 * margin`.
     * In partitionColumns(): Strict upper-bound validation: `tileWidth = minOf(effectiveMaxTileW, maxOf(limits.minPageWidth, groupTotalTableWidth + 2 * limits.margin))` guaranteeing `tileWidth <= effectiveMaxTileW <= 14400f`.
     * In partitionRows(): Strict upper-bound validation: `tileHeight = minOf(effectiveMaxTileH, maxOf(limits.minPageHeight, limits.headerHeight + groupHeight + 2 * limits.margin + limits.bannerHeight * 2))` guaranteeing `tileHeight <= effectiveMaxTileH <= 14400f`.
     * Oversized individual rows in tiled mode: Must chunk lines into vertical row fragments across tiles so no tile height exceeds the limit!

2. FULL MERGED-CELL GEOMETRIC PRESERVATION (P0):
   - Current Defect: In OfficeConverter.kt, `mergedRegions` was only checked to decide `shouldDrawText = (rIdx == firstRow && colIndex == firstCol)`. The cell was still drawn with individual column width and individual row height, leaving internal gridlines and failing to expand the visual box.
   - Requirement:
     * Compute full merged bounds:
       Total Merged Width = sum of `colWidths[c]` for `c` in `firstCol..lastCol`.
       Total Merged Height = sum of `rowHeights[r]` for `r` in `firstRow..lastRow`.
     * Internal cell gridlines inside the merged region must NOT be drawn. Only the outer boundary of the merged region receives borders!
     * Text in the merged region must be wrapped and formatted across the full merged width `(totalMergedWidth - 8f)`!
     * Tile-Boundary Merges: When a merged region spans across a horizontal or vertical tile boundary, the layout engine and renderer must compute the intersection rectangle of the merged cell with the tile's visible row and column ranges:
       - On the tile containing the anchor cell, render the merged rectangle with outer borders and anchor text.
       - On the subsequent continuation tile, render the continuation slice with outer borders (top/bottom/right) and an open left border (or subtle `(cont.)` marker) without duplicate text or internal gridlines!

3. STRICT CELL ORDERING ASSERTION IN INTEGRITY TEST (P0):
   - Current Defect: `testXlsxTiledContentIntegrityCellIdExactMatchNoDuplicatesNoLoss` only asserted `count == count` and `set == set`. A reverse-ordered or jumbled output would pass.
   - Requirement:
     * Compute the exact expected row-major reading sequence:
       For each tile (Row Panel $R_i$, Col Panel $C_j$ in row-major order):
         For each row $r$ in $R_i$:
           For each col $c$ in $C_j$:
             Yield expected cell token.
     * Assert `assertEquals("Extracted cell ID sequence must match expected row-major reading order across tiles exactly", expectedSequence, extractedMatches)`.

4. EXCEL FROZEN-PANE XML METADATA PARSING (P1):

   - Requirement:
     * Parse `<pane xSplit="N" ySplit="M" state="frozen"/>` inside `<sheetViews><sheetView>` in `OpenXmlDocumentParser.kt`.
     * Populate `frozenColumnsCount = xSplit ?: 0` and `frozenRowsCount = ySplit ?: 0` on `XlsxSheetData`.

SECTION 4: BROADER ARCHITECTURAL AND EDGE-CASE RESILIENCE PLAN
================================================================================
1. Zero PDF Coordinate Violations:
   - PDF coordinate overflow (> 14,400 pt) causes catastrophic failure in standard PDF rendering engines. By enforcing mathematical ceilings at both the layout engine level and rendering level, no page can ever exceed 14,400 pt unless explicitly scaled through Level 2 /UserUnit.

2. True Merged Cell Aesthetics & Data Integrity:
   - In Excel, merged cells merge both geometry and content:
     * Inner cells become whitespace within the outer perimeter.
     * Text alignment is centered or top-left inside the full merged perimeter.
     * When intersecting a tile boundary, the outer perimeter line should reflect that the cell continues across the panel boundary.

3. Complete Sequence Preservation:
   - In 2D tiled spreadsheets, the reader navigates:
     Page 1: Top-Left (Row Group 1, Col Group 1)
     Page 2: Top-Right (Row Group 1, Col Group 2)
     ...
     Page K: Next Vertical Tier (Row Group 2, Col Group 1)
   - Every single cell ID must be verified in the exact physical reading sequence.

4. Android PdfRenderer Interoperability:
   - Testing with Android `PdfRenderer` proves that Android's native PDF viewing stack (used by Google Drive PDF Viewer, Files by Google, and system print preview) handles the generated PDF /UserUnit without rendering artifacts.
