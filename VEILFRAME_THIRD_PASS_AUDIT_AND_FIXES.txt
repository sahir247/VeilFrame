### 1. JNI string and model cleanup is not fully exception-safe

Priority: High

The new catch blocks prevent many C++ exceptions from crossing JNI, but catching an exception does not automatically release resources acquired before the exception.

For example, in `matting_jni.cpp`:

* `GetStringUTFChars()` acquires `param_c` and `bin_c`.

* Subsequent native allocations and model initialization can throw.

* The catch blocks return `JNI_FALSE`, but they do not guarantee both UTF buffers are released.

There is a similar risk in RIFE: constructing `dir_str` can throw after `GetStringUTFChars()` succeeds but before `ReleaseStringUTFChars()` executes.

Recommended fix: create a small RAII wrapper for JNI UTF strings and use `std::unique_ptr<ncnn::Net>` during model initialization. Transfer ownership to the global model pointer only after successful loading.

### 2. The 10,000-row gap cap can misplace valid spreadsheet data

Priority: Medium

The parser currently pads missing rows only when:

```kotlin
if (gap in 1..10000)
```

That protects against huge allocations, but it also creates a correctness problem.

If a legitimate worksheet contains a cell at row 20,000 after row 1, the parser does not preserve the missing rows. It appends the later row immediately after the previous parsed row.

The data is retained, but its vertical position is wrong.

Recommended fix: do not allocate thousands of empty lists. Use a sparse row representation or reject oversized gaps with a clear conversion error. Never silently shift valid data.

Also test duplicate and out-of-order explicit row numbers.

### 3. PDF pagination has improved, but the fidelity test is not a geometry test

Priority: Medium

The oversized-row test is now materially stronger: it verifies that all 60 line identifiers appear in the PDF and that the document has at least two pages.

That is good evidence of text retention.

However, it does not verify:

* Each line appears exactly once.

* Lines appear in the correct order.

* Text stays inside the corresponding cell.

* Cell borders remain continuous across page breaks.

* Adjacent cells do not overlap.

The sparse-row PDF test likewise checks text presence, not actual vertical spacing.

Recommended fix: use `PDFTextStripper` with positional output, then assert line order and bounding boxes. Add a fixture with multiple columns and a long multiline cell.

### 4. RealSR deserves a separate JNI exception audit

Priority: Medium

The latest commit's exception-containment changes focus on PII, matting and RIFE. RealSR has ten exported JNI functions, so it should be audited independently for the same standard.

I would not infer that every RealSR entry point is protected simply because the adaptive enhancement and Lanczos paths have catch blocks.

SECTION 2: COMPREHENSIVE FINDINGS MAPPING
================================================================================

Finding 1 [High]: JNI String and Model Cleanup Exception Safety
- Target files: `android/app/src/main/cpp/matting_jni.cpp`, `rife_jni.cpp`, `realsr_jni.cpp`
- Problem:
  1. `env->GetStringUTFChars()` returns raw C string pointers. If any subsequent C++ allocation (`new ncnn::Net()`, `std::string`, `vector::resize`), lock, or model parse throws an exception, catch blocks return early without calling `env->ReleaseStringUTFChars()`.
  2. In `matting_jni.cpp`, `ncnn::Net* net = new ncnn::Net();` is allocated with raw `new`. If `load_param` or `load_model` throws, the allocated `net` leaks on exception exit paths.
- Solution:
  1. Introduce a reusable move-only RAII helper `veilframe::JniUtfStringScope` in `jni_utf_scope.h` that guarantees `ReleaseStringUTFChars()` is invoked upon scope exit, error returns, or unhandled exceptions.
  2. Use `std::unique_ptr<ncnn::Net>` during model initialization and loading. Only transfer ownership to the global pointer upon complete, validated success.

Finding 2 [Medium]: Explicit XLSX Row Gap Handling Without Silent Misplacement
- Target files: `android/app/src/main/java/com/veilframe/app/pdf/operations/OpenXmlDocumentParser.kt`, `OfficeConverter.kt`
- Problem:
  The current check `if (gap in 1..10000)` prevents excessive list allocations for extreme row indices, but if a legitimate spreadsheet has a cell at row 20,000, it drops the gap and appends the row immediately after the preceding row, silently shifting vertical positions and destroying sheet layout fidelity.
  Furthermore, duplicate `<row r="...">` elements or out-of-order rows in the XML stream can cause erratic row ordering or collision.
- Solution:
  1. Implement a structured sparse row representation:
     `data class XlsxRow(val rowIndex: Int, val cells: List<String>)`
     `data class XlsxSheetData(val name: String, val sparseRows: List<XlsxRow>, val rows: List<List<String>>)`
  2. In `parseWorksheet`, collect rows into a `TreeMap<Int, MutableList<String>>` keyed by 1-based `rowIndex`.
     - Automatically sorts out-of-order `<row>` elements.
     - Merges duplicate row definitions cell-by-cell without data loss.
  3. Validate row gaps explicitly:
     - Allow spacer row padding up to a well-defined printable limit (`MAX_SPACER_ROWS = 500`).
     - If an excessive gap (> 500 rows) exists between rows, reject the conversion with an informative `IllegalArgumentException` explaining that extreme sparse row gaps cannot be rendered continuously without truncation or thousands of blank pages. Never silently shift data rows vertically!

Finding 3 [Medium]: PDF Geometry, Line Ordering, and Positional Verification
- Target files: `android/app/src/test/java/com/veilframe/app/pdf/operations/OfficeConverterFidelityTest.kt`
- Problem:
  Current tests verify that all 60 line identifiers exist somewhere in the PDF, but do not assert:
  - Exact single appearance (no duplicate line generation).
  - Strict top-to-bottom reading/line order across pages.
  - Coordinate containment inside designated cell column bounds.
  - Absence of text bounding box overlap between adjacent columns.
  - Verifiable vertical distance in sparse-row layouts.
- Solution:
  1. Build a positional text extractor subclassing `com.tom_roush.pdfbox.text.PDFTextStripper` that captures `TextPosition` metadata (`x`, `y`, `width`, `height`, `pageIndex`).
  2. Add multi-column test fixtures containing both short title cells and long 60-line multiline cells.
  3. Assert:
     - Each line appears exactly once.
     - Line order is monotonic (`y` coordinate decreases down the page; page index increases monotonically).
     - Column text bounding boxes do not overlap in horizontal space.
     - Sparse-row vertical spacing reflects the explicit row gaps physically.

Finding 4 [Medium]: RealSR JNI Exception Containment Audit & Hardening
- Target file: `android/app/src/main/cpp/realsr_jni.cpp`
- Problem:
  RealSR has 12 exported JNI functions:
  `nativeGlobalInit`, `nativeGlobalDestroy`, `nativeGetGpuCount`, `nativeGetGpuDeviceName`, `nativeCreateInstance`, `nativeDestroyInstance`, `nativeCancel`, `nativeLoadModel`, `nativeProcessStreaming`, `nativeProcessStripStreaming`, `nativeAdaptiveDetailEnhance`, `nativeScaleLanczos4`.
  Several functions (`nativeGlobalDestroy`, `nativeGetGpuCount`, `nativeGetGpuDeviceName`, `nativeCreateInstance`, `nativeDestroyInstance`, `nativeCancel`) lack comprehensive outer try-catch blocks or use manual string cleanup.
- Solution:
  1. Audit all 12 functions in `realsr_jni.cpp`.
  2. Wrap every entry point in `try { ... } catch (const std::bad_alloc&) { ... } catch (const std::exception&) { ... } catch (...) { ... }` blocks with error logging and defined return codes.
  3. Use `veilframe::JniUtfStringScope` in `nativeLoadModel` for `paramPath` and `binPath`.

SECTION 4: BROADER EDGE-CASE AND ARCHITECTURAL PLAN
================================================================================

1. Out-of-Order and Duplicate Row Merging:
   If an XLSX document contains `<row r="3"><c r="A3"><v>A</v></c></row>` followed by `<row r="3"><c r="B3"><v>B</v></c></row>`, cell A3 must not be discarded. Cell B3 must merge into the existing row at targetCol 1, preserving cell A3 at targetCol 0.

2. Negative or Zero Row Numbers:
   If hostile XML specifies `<row r="-1">` or `<row r="0">`, ignore or sanitize to positive 1-based indexing to prevent underflow or array out-of-bounds.

3. Malicious Huge Gaps:
   A gap such as `r="1"` followed by `r="1000000"` will attempt to allocate a million list objects if unchecked, causing OOM. Rejection with an explicit error message prevents DoS while upholding strict spatial fidelity.

4. Multi-Page Coordinate Tracking in PDF:
   PDF coordinates have origin (0, 0) at the bottom-left, while `PDFTextStripper` converts `yDirAdj` from the top of the page. The geometry verification must account for page boundaries: within a single page, `yDirAdj` strictly increases downwards; across page breaks, pageIndex increases monotonically.

5. RAII Exception Safety in Native Code:
   Any JNI call that acquires VM-managed buffers (`GetStringUTFChars`, `GetPrimitiveArrayCritical`, `GetDirectBufferAddress`) must have an active RAII guard on the stack before any allocation or compute function is invoked.
