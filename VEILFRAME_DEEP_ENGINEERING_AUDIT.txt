2. CRITICAL BUGS
================

C-01 PRE-RENDERED QR CAN BECOME ANIMATION SOURCE
Severity: P0 / Confidence: CONFIRMED
File: android/app/src/main/java/com/veilframe/app/qr/ui/QrStudioViewModel.kt
Functions: saveGif(), saveVideo(), saveAnimatedSvg()

Fallback source selection:
  val baseBmp = _state.value.sourceImage ?: _state.value.backgroundImage ?: _state.value.bitmap
  _state.value.bitmap is the already-rendered QR preview.
Then: ImageSource.Animated(frames.map { it.bitmap }, frames.map { it.durationMs })
placed back into QrDesign.imageSource.

Data flow: User design -> regenerate() -> generateWithResult() -> _state.bitmap = rendered QR
          -> saveGif/saveVideo/saveAnimatedSvg -> fallback to _state.bitmap
          -> ImageSource.Animated(QR bitmap) -> AnimatedQrGenerator -> re-render QR around QR

Reproduction: Enter URL. Select any static QR style. Do NOT import an image/video.
Generate preview. Press GIF/animated SVG/video export.
Expected: No animation source -> reject animated export, or use only actual source media.
Actual:   No animation source -> use rendered QR bitmap -> re-render QR around QR.

Fix: Remove _state.value.bitmap from all source-artwork fallbacks.
Never use rendered preview bitmap as an input ImageSource.
The compatibility API in QrExporter already recognizes and documents protection against this.
The ViewModel currently bypasses that safety boundary.
Status: RESOLVED (2026-10-01) - Removed _state.value.bitmap from saveGif, saveVideo, saveAnimatedSvg fallback chains. When artwork is absent, export is cleanly rejected with user guidance. Verified with unit test testAnimationExportsRejectWhenNoArtworkSourcesProvidedEvenIfPreviewBitmapExists.

C-02 NORMAL UI GENERATION IS NOT EFQRCode ENCODER PARITY FOR BASIC
Severity: P1 / Confidence: CONFIRMED
File: QrGenerator.kt / Function: defaultModeFor()

SAFE uses QrEncoder.encode() (ZXing) rather than VeilQrEncoder.encode().
SAFE also uses AUTO -> M; EFQRCode default is H.
Result: EFQRCode-compatible encoder != default BASIC UI encoder.
Fix: Separate EF parity API -> VeilQrEncoder -> EF defaults
     from  Safe QR API  -> ZXing -> safety-oriented defaults.
Status: RESOLVED (2026-10-01) - Canonical generateEfCompatible() and generateSafe() entry points established. QrGenerator.defaultModeFor() and QrStudioViewModel.UiState.generationMode strictly default to GenerationMode.PARITY_EF (VeilQrEncoder with EC Level H and 1-module margin default), delivering true EFQRCode 7.0.3 encoder parity for basic QR codes out-of-the-box. Safe production mode remains selectable via GenerationMode.SAFE or generateSafe().

C-03 UI BUILDS AN EXPLICIT 4-MODULE QUIET ZONE WHERE EF DEFAULTS TO 1
Severity: P1 / Confidence: CONFIRMED
File: QrStudioViewModel.kt / Function: buildDesignFromState()

EF basic default ~1 module margin vs VeilFrame QR Studio default 4 modules for most styles.
explicitQuietZone was explicitly populated even when quietZoneChoice was null, preventing PARITY_EF from restoring EF defaults.
Fix: Separate EF default geometry (qz=1) from safe geometry (qz=4) via explicit policy objects.
Status: RESOLVED (2026-10-01) - Introduced QrGeometryPolicy (EfParity with 1-module margin vs SafeProduction with 4-module margin). explicitQuietZone is now strictly null unless explicitly chosen by the user, allowing EF parity mode to apply 1-module margins unhindered.

C-04 GENERATION CAN REPORT SUCCESS WITH A FAILED SCANABILITY REPORT
Severity: P1 / Confidence: CONFIRMED
File: QrGenerator.kt / Function: generateWithResult()

Returns QrRenderResult.Success(...) even if report.isScanReady == false.
Callers can receive Success + QR that failed scanability validation.
Fix: Introduce Success.Unverified / Success.Verified / Failure typed states.
Status: RESOLVED (2026-10-01) - Introduced Success.Verified and Success.Unverified typed states with isVerified property and backwards-compatible companion invoke.

5. ENCODER PARITY
==================
Assessment: Strong parity / Confidence: CONFIRMED from committed upstream oracle test corpus

EF pipeline:  String -> QR8bitByte -> UTF-8 bytes -> QRCodeModel -> version -> RS blocks
              -> mask candidates 0-7 -> lost-point scoring -> best mask -> format info -> matrix
Veil pipeline: String -> Charsets.UTF_8 -> VeilQrEncoder -> QRCodeModel (Kotlin port)
               -> RS blocks -> mask scoring -> function-pattern placement -> QrMatrix
Coordinate translation: model.isDark(row,col) -> matrix.isDark(col,row) [expected]

Encoding conclusion:
  Byte mode / UTF-8 / Unicode bytes / Version selection / RS blocks / Mask scoring: MATCH
  Natural masks / Forced masks / V40 / Matrix orientation / Structure: MATCH / STRONG

Remaining caveat: oracle is pre-generated; fresh EFQRCode vs fresh VeilFrame not executed here.

6. GEOMETRY PARITY
===================
Overall: PARTIAL / structurally strong

Good: QrGeometry is correctly matrix-aware; supports square/non-square, asymmetric/fractional
quiet zones, centering, directional insets, different output sizes, content-relative logo centering.

Important problem: QrGeometry.resolveQuietZone(design, matrixSize=21) is semantically dangerous.

7. ARTISTIC STYLE PARITY
=========================
All styles: PARTIAL or PARTIAL/CLOSE or PARTIAL/HIGH EFFORT.
None fully proven by independent pixel oracle.

BUBBLE: EF uses unseeded Double.random; VeilFrame uses deterministic hash-derived randomness.
  Excellent for reproducibility but not exact EF visual reproduction.
LINE: EF uses availability graph + directional runs. VeilFrame adds circuit bridges, accent rings.
  EF mode should be kept separate from Veil enhanced mode.
RANDOM RECTANGLE: Same two-rectangle model, but VeilFrame uses split seeded RNG streams
  (shuffleRng, scaleRng, colorRng, offsetRng) while EF uses system randomness.
  Assessment: APPROXIMATE PARITY
RESAMPLE IMAGE: VeilFrame recreated 3x3 subpixel domain, gamma/luminance processing, role-aware
  exclusions, center anchors, backdrop separation, stochastic sampling, deterministic mode, IR/SVG.
  Missing proof: independent pixel comparison across real source images and platform rasterizers.
  Assessment: HIGH-EFFORT PARTIAL PARITY

14. MEMORY / PERFORMANCE / LOW-RAM AUDIT
=========================================
Preview capped at minOf(outputSize, 512) -- GOOD

Export peak:
  4096x4096 ARGB_8888 = 64 MiB per bitmap.
  Two full-size renders during static export ~= 128 MiB before buffers.
  15 animation frames at full resolution ~= 960 MiB -- NOT ACCEPTABLE as default retained in-memory.
  SVG: base64 expansion increases binary size by ~4/3.

Recommended architecture:
  Preview: 512px max
  Static export: render once -> validate same bitmap -> encode/save -> release bitmap
  Animated export: streaming frame renderer -> encode frame -> release frame -> next frame (At most one rendered QR frame bitmap is intentionally retained by the streaming renderer at a time)

Assessment: Preview GOOD / Export memory RESOLVED for static single-render and streaming animation frame pipelines
