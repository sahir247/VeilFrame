### Bottom line

VeilFrame has achieved **substantial algorithmic parity**, especially in its QR matrix encoder and several geometry/image primitives. However, it does **not** currently achieve EFQRCode-level behavioral parity across the entire requested scope.

The biggest reasons are:

1. the EF stochastic styles are not sequence-identical because VeilFrame deliberately introduces deterministic seeded PRNGs;
2. the default D25 quiet-zone behavior differs from EFQRCode;
3. the public legacy `QrGenerator.generate(..., ecLevel)` API ignores its supplied EC level;
4. the advertised SAFE path does not actually normalize to the documented 4-module quiet zone;
5. scanability validation can report a QR as scan-ready despite a non-standard quiet-zone warning;
6. SVG export is validated against the Canvas bitmap rather than against the actual SVG after independent rasterization;
7. the UI deliberately uses a different preview resolution from export;
8. UI input is `.trim()`ed before encoding;
9. some UI style paths are dispatched through VeilFrame's generalized compositional renderer rather than the dedicated EF-compatible renderer;
10. the animation/SVG implementation is structurally different from EF's image-animation semantics;
11. the existing tests are overwhelmingly **self-consistency tests**, not independent EFQRCode oracle tests.

So the appropriate current verdict is:

# **PARTIAL PARITY**

# 2. CRITICAL BUGS

## C1 — Public `ecLevel` argument is ignored

**Severity:** P0 — correctness/blocking
**Confidence:** **CONFIRMED**

**File**

`android/app/src/main/java/com/veilframe/app/qr/QrGenerator.kt`

**Function**

`generate(content, params, ecLevel)`

**Relevant region**

Around the legacy API near line 539.

The function accepts:

```text
ecLevel: ErrorCorrectionLevel = ...
```

but then does:

```text
val design = QrDesign.fromQrStyleParams(params)
val result = generateWithResult(content, design)
```

The supplied `ecLevel` is never copied into `design.correction`.

The eventual encoder therefore uses the design's correction setting rather than the caller's argument.

### Reproduction

Conceptually:

```kotlin
QrGenerator.generate(
    "HELLO",
    QrStyleParams(),
    ErrorCorrectionLevel.L
)
```

does **not** guarantee EC-L.

The `QrDesign` created from the params starts with AUTO semantics, and `generateMatrix()` resolves AUTO to H for artistic/parity modes.

### Expected

Passing `L` must produce EC-L.

### Actual

The argument can be ignored.

### Fix

Either remove the legacy argument entirely or make it authoritative:

```text
params → design
design.correction = explicit ecLevel
→ generation
```

There must be exactly one EC source of truth.

## C2 — SAFE mode advertises a 4-module quiet zone but does not enforce it

**Severity:** P0
**Confidence:** **CONFIRMED**

**Files**

`android/app/src/main/java/com/veilframe/app/qr/QrGenerator.kt`

`android/app/src/main/java/com/veilframe/app/qr/model/QrDesign.kt`

`android/app/src/main/java/com/veilframe/app/qr/model/QrGeometry.kt`

### Data flow

`generateSafe()`

→ `generateWithResult(..., GenerationMode.SAFE)`

→ `effectiveDesignForMode()`

→ geometry

But `effectiveDesignForMode()` only performs special normalization for `PARITY_EF`.

For SAFE it returns the supplied design unchanged.

`QrDesign()` defaults to 1 module, while `generateSafe()`'s documentation says it provides the standard 4-module quiet zone.

### Result

The implementation and its public contract disagree.

The problem is aggravated by `ScanabilityValidator` because the validator can warn about `<4` modules without making quiet-zone adequacy part of `isScanReady`.

### Fix

Create a canonical `SAFE` normalization:

```text
SAFE:
  EC = policy-resolved
  QZ >= 4 unless caller explicitly opts out
  validation must require the same policy
```

## C3 — Scanability gate does not actually gate the quiet-zone requirement

**Severity:** P0/P1
**Confidence:** **CONFIRMED**

**File**

`android/app/src/main/java/com/veilframe/app/qr/validation/ScanabilityValidator.kt`

**Function**

`performValidation()`

The validator computes:

```text
quietZoneReport.hasFourModuleMargin
```

and emits:

```text
"Quiet zone is less than the standard 4 modules margin."
```

but `isScanReady` ultimately depends primarily on successful decode plus logo constraints:

```text
decodeMatches
&& !logoReport.hasProtectedOverlap
&& logoReport.isWithinErrorCorrectionCapacity
```

The quiet-zone result is not itself a hard requirement for scan readiness.

Therefore a QR can conceptually be:

```text
quietZone warning = FAIL
decode = PASS
isScanReady = true
```

### Why this matters

Your stated safety contract is not merely “ZXing happened to decode this bitmap.” It is a structural production-safe QR contract.

### Fix

Make policy explicit:

```text
ScanabilityPolicy.standard:
    quietZone >= 4
    contrast >= threshold
    finder integrity
    decoder pass
    logo budget
```

Then use that same policy for `SAFE`, preview diagnostics, and export.

## C4 — SVG export is validated through the bitmap path, not through the SVG output

**Severity:** P1
**Confidence:** **CONFIRMED**

**File**

`android/app/src/main/java/com/veilframe/app/qr/ui/QrStudioViewModel.kt`

**Function**

`saveSvg()`

The flow is:

```text
QrGenerator.generateWithResult()
        ↓
Canvas Bitmap
        ↓
ScanabilityValidator.validateStrict(bitmap)
        ↓
QrGenerator.generateSvg()
        ↓
save SVG
```

The SVG itself is never rasterized and decoded before being accepted.

That is directly contrary to the required Canvas/SVG audit condition in the supplied specification.

### Failure mode

A bitmap renderer can be correct while SVG differs in:

* masks
* embedded image scale
* gradient coordinates
* clip paths
* SVG transform offsets
* ID references
* fractional coordinates
* alpha
* image `preserveAspectRatio`
* animation references

The existing test suite recognizes the distinction, but the production export path does not close that loop.

### Fix

For SVG:

```text
generate SVG
→ rasterize with an independent SVG renderer
→ scanability validation
→ optionally compare with canonical Canvas geometry
→ save
```

## C5 — UI silently removes payload whitespace

**Severity:** P1
**Confidence:** **CONFIRMED**

**File**

`android/app/src/main/java/com/veilframe/app/qr/ui/QrStudioViewModel.kt`

**Functions**

`regenerate()`, `saveToGallery()`, `saveSvg()`, etc.

The UI repeatedly uses:

```text
s.content.trim()
```

before encoding.

That means:

```text
" abc "
```

becomes:

```text
"abc"
```

This changes the QR payload.

EFQRCode's QR generator does not define this as a preprocessing semantic.

### Fix

Do not trim payload data.

Use:

```text
isBlank() → validation only
original content → encoder
```

## C6 — Default D25 quiet zone does not match EFQRCode

**Severity:** P1
**Confidence:** **CONFIRMED**

EFQRCode:

`Source/Styles/EFQRCodeStyle25D.swift`

uses:

```text
EFStyleParamBackdrop()
```

and EF's default backdrop `viewBox()` returns:

```text
x = -1
y = -1
width = moduleCount + 2
height = moduleCount + 2
```

when no explicit quietzone is provided.

Therefore D25's default is still one module around the QR.

VeilFrame:

`android/app/src/main/java/com/veilframe/app/qr/model/QrGeometry.kt`

contains:

```text
resolveDefaultQuietZone(...)

    else -> 1
```

That is a concrete reference-behavior mismatch.

The local test `testArtisticDefaultQuietZoneSemantics()` actually locks in the VeilFrame rule rather than testing it against an EFQRCode-generated oracle.

Default D25 to one module in EF parity mode.

If VeilFrame intentionally wants zero-QZ D25 as an extension, that should be an explicit VeilFrame profile, not the EF parity default.

# 5. ENCODER PARITY

## Architecture

### EFQRCode

```text
String / Data
      ↓
QRCode
      ↓
QRCodeModel
      ↓
QR8bitByte
      ↓
typeNumber
      ↓
createData()
      ↓
Reed-Solomon
      ↓
8 mask candidates
      ↓
lostPoint()
      ↓
best mask
      ↓
makeImpl()
      ↓
finder / alignment / timing / format / version / data
```

### VeilFrame

```text
String
 ↓
VeilQrEncoder
 ↓
UTF-8 bytes
 ↓
QRCodeModel
 ↓
type/version selection
 ↓
createData()
 ↓
RS generation/interleave
 ↓
mask search
 ↓
matrix
 ↓
QrMatrix + FunctionPatternMask/type table
```

This portion is very close.

### CONFIRMED parity

EF's actual generator uses byte mode:

`Source/QRCodeSwift/QRCodeModel.swift`

constructs `QR8bitByte(data)` rather than dynamically segmenting numeric/alphanumeric/Kanji data.

VeilFrame's:

`android/app/src/main/java/com/veilframe/app/qr/encoder/engine/VeilQrEncoder.kt`

does the same conceptual operation with UTF-8 bytes.

Both implement the qrcode.js family of:

* BCH
* GF(256)
* RS polynomial
* RS block tables
* format bits
* version bits
* mask penalties
* data placement.

The `VeilQrEncoderParityTest` and `VeilGoldenCorpusTest` exercise V1 through V40 boundaries and decode matrices using ZXing.

### Important limitation

The tests are **not an independent EF oracle**.

For example, `VeilGoldenCorpusTest` records an expected version in VeilFrame test data and then verifies VeilFrame against that expected number. It never loads an EF-generated matrix and diffs the matrices.

Therefore:

> Source-level algorithm parity: **CONFIRMED**
> Empirical bit-for-bit parity against EF-generated vectors: **UNVERIFIED**

### Unicode

For default UTF-8 text:

```text
ASCII
Hindi/Bengali
Japanese
Chinese
emoji
mixed Unicode
```

the encoder architecture is compatible.

But EF exposes a String/Data encoding API while Veil's primary String API hardcodes UTF-8.

That is:

**Default UTF-8 parity: CONFIRMED**

**All EF encoding-input semantics: PARTIAL**

### Mask parity

The lost-point implementation is clearly derived from the qrcode.js algorithm used by the reference dependency.

The mask-selection algorithm therefore looks correct.

Again, however, no permanent test compares:

```text
EF selected mask
vs
Veil selected mask
```

for the same byte stream over the full matrix corpus.

# 6. GEOMETRY PARITY

## Canonical Veil geometry

`android/app/src/main/java/com/veilframe/app/qr/model/QrGeometry.kt`

uses:

```text
totalModulesX =
    matrixSize + leftQZ + rightQZ

totalModulesY =
    matrixSize + topQZ + bottomQZ

moduleSize =
    min(moduleWidth,moduleHeight)
```

and centers the QR inside non-square output.

The central module conversion:

```text
x = offsetX + col * moduleSize
y = offsetY + row * moduleSize
```

is coherent.

### Strength

VeilFrame correctly avoids a hard-coded Version-1 matrix assumption.

That is important for V2/V5/V10/V20/V30/V40.

### Quiet-zone resolver

Veil does have an authoritative resolver:

`QrGeometry.resolveQuietZone(design, matrixSize)`

with:

```text
fractional
→ directional
→ explicit
→ design default
```

This is architecturally better than having every renderer independently calculate the margin.

But the D25 default differs from EF as described above.

### Fractional/asymmetric margins

Veil supports more expressive geometry than the EF default API.

That is an intentional VeilFrame innovation.

The issue is not the existence of the feature; the issue is ensuring that:

```text
Canvas
SVG
logo
background
image sampling
animation
validation
```

all consume the same resolved floating-point geometry.

The core geometry object does this well; several renderer-specific paths still perform their own coordinate conversions.

### Main geometry risk

There are multiple geometry systems:

```text
QrGeometry
BasicGeometryBuilder
QrGeometryIr
style-specific geometry
D25 geometry
ResampleGeometryBuilder
SvgExporter manual geometry
VeilPositionPatternGeometry
```

This is manageable, but it means the invariant “one canonical coordinate space” is not yet fully enforced architecturally.

## BUBBLE

**Status: PARTIAL PARITY**

EF implementation:

`Source/Styles/EFQRCodeStyleBubble.swift`

uses `Double.random`.

* cross stroke
* cross center
* 2×2 stroke
* pair radius
* pair stroke


**Intentional difference, not a regression.**

# 8. IMAGE PIPELINE PARITY

## EF reference

`Source/Type/EFImageMode.swift` defines:

* `scaleToFill`
* `scaleAspectFit`
* `scaleAspectFill`

including image preprocessing before SVG insertion.

Veil:

`android/app/src/main/java/com/veilframe/app/qr/image/EfImagePreprocessor.kt`

and:

`ImageScaleResolver.kt`

implement equivalent concepts.

Veil explicitly models letterboxing as white padding.

This is good and well-tested.

### Resample

The intended pipeline is:

```text
source image
→ aspect mode
→ pre-scale to 3N × 3N
→ subpixel sampling
→ QR functional mask
→ threshold
→ stochastic dots
```

This is structurally very close to EF's `getGrayPointList()` route.

### Major caveat

In generic background drawing:

`QrGenerator.drawBackground()`

preprocesses a backdrop and then passes the preprocessed bitmap through another `resolveSrcDst(... ASPECT_FILL)` stage.

**Confidence: LIKELY**

This needs a source-image coordinate test using deliberately asymmetric images such as:

```text
400×100
100×400
```

with visible red/green/blue corner markers.

### Backdrop/source separation

Veil is better architecturally than a naïve port because it explicitly separates:

```text
imageSource
backgroundLayer
resample backdrop
backdropStyle
logo
```

That is a legitimate VeilFrame improvement.

# 9. CANVAS vs SVG PARITY

This is currently one of the biggest audit gaps.

### What is good

Veil introduced a common IR:

```text
QrGeometryIr
QrGeometryNode
IrCanvasRenderer
IrSvgRenderer
```

That is the right architectural direction.

The `Basic` path makes substantial use of it.

`JvmCanvasVsSvgDifferentialTest` also actually rasterizes SVG and compares pixels.

### What is not sufficient

The strongest JVM test covers primarily:

* basic square
* rounded
* circle
* diamond
* finder variants
* gradient
* corner radius
* quiet zone
* non-square dimensions.

It does **not** establish full EF parity across:

* Bubble
* D25
* DSJ
* Image
* ImageFill
* Line
* RandomRectangle
* Resample
* animated SVG
* logos
* embedded image cropping
* full mask composition.

And its SVG oracle is still VeilFrame's own `DeterministicSvgRasterizer`.

So:

```text
Canvas vs Veil SVG self-consistency: STRONG
Canvas vs EF SVG behavior: UNVERIFIED
Canvas vs independent browser/CoreGraphics rendering: UNVERIFIED
```

### Known architectural divergence

`SvgExporter.generateSvg()` contains style-specific manual generation functions:

```text
generateImageFillSvg

generate25DSvg
generateBubbleSvg
generateDsjSvg
generateFunctionSvg
generateLineSvg

```

while Canvas frequently goes through different renderer classes.

That means:

> “Both use the same QrDesign” does not imply “both use the same rendering algorithm.”

This is precisely the failure mode the supplied audit brief asked to look for.

# 10. LOGO / MASK / CLIPPING PARITY

## Strengths

`QrGeometry.computeLogoRect()` anchors the logo to the QR content region rather than the full canvas.

That is the right coordinate system for asymmetric quiet zones.

Veil also has explicit:

* logo shape
* scale
* border
* alpha
* image scale mode.

## Risk

`ScanabilityValidator.mapPixelRectToModules()` maps logo rectangles back into module coordinates using integer truncation.

That means boundary-touching cases are sensitive to:

```text
left/right exact integer boundary
fractional QZ
fractional module size
```

This needs differential tests for:

```text
logo exactly on a module edge
logo ±0.01 module
QZ 0 / 1 / 4 / 4.5
non-square canvas
```

### Finder overlap

Veil deliberately rejects logo overlap with protected patterns.

That is safer than blindly drawing.

But EF's logo/icon behavior should be compared geometrically, not merely by whether both reject/accept.

---

# 11. ANIMATION / EXPORT PARITY

## Static image animation

Veil has a strong source-frame abstraction:

```text
QrFrame(bitmap,durationMs)
```

and a timeline-based selector.

`renderFrameResultAt()` handles:

* animated source
* animated logo
* cumulative timing.

That is good.

## Streaming

`renderFramesStreaming()` is a substantial improvement over retaining every rendered frame.

This is useful for 6–16 GB devices.

But the bitmap ownership contract should be explicit:

```text
onFrameRendered(...)
→ callback owns frame
→ callback MUST recycle/release
```

or better, the streaming abstraction should enforce it.

---

## Animated SVG

This is a larger parity issue.

The generic implementation does:

```text
for each frame:
    generate complete SVG
    extract inner SVG
    put it in <defs><g id=frame_n>
```

then:

```xml
<use ...>
  <animate attributeName="xlink:href"
           values="..."
           keyTimes="..."
           calcMode="discrete" />
</use>
```

This is not the same strategy as EF's image-source animation.

For EF's image-style animation, the reference keeps the QR structure/static layers outside the image animation and changes the image source.

Veil's generic path can duplicate substantially more structure.

### Additional issue

`generateAnimatedSvg()` builds all frame SVG strings before returning.

For large images/frames:

```text
memory ≈ Σ(frame SVG size)
```

rather than streaming.

This is a significant low-RAM risk.

---

## Already-rendered QR treated as source artwork?

I did **not** find a source-backed proof that the main production path takes `renderResult.bitmap` and re-renders a second QR on top of it.

The normal animation paths use source images / source frames.

Therefore this specific defect remains:

**UNVERIFIED**

and should not be declared a bug without a targeted end-to-end regression test.

# 12. PUBLIC API / ESCAPE-HATCH AUDIT

The API surface now contains several overlapping concepts:

```text
QrDesign
QrStyleParams
QrFrame
Bitmap
QrMatrix
ImageSource
ImageSourceStyle
QrOutputFormat
GenerationMode
```

This is powerful but creates bypass opportunities.

### Safe/canonical APIs

The best current path is approximately:

```text
QrGenerator.generateWithResult()
QrGenerator.generateSvg()
QrExporter.exportTyped()
```

### Risky legacy APIs

Examples:

```text
QrGenerator.generate()
generatePng()
generateJpeg()
AnimatedQrGenerator.renderFrameAt()
AnimatedQrGenerator.renderFrames()
```

These frequently:

* return nullable/raw values
* convert errors to exceptions
* bypass newer typed contracts
* expose renderer-specific behavior.

The ignored `ecLevel` argument in `generate()` is the clearest example of a dangerous compatibility API.

### Recommendation

Make all legacy APIs explicit adapters:

```text
legacy API
→ canonical QrDesign
→ canonical GenerationMode
→ canonical generator
```

No legacy API should contain independent QR semantics.

# 13. UI AUDIT

## State → Design mapping

`QrStudioViewModel.buildDesignFromState()` is comprehensive and maps a very large amount of state into `QrDesign`.

That is good.

The mapping includes:

* EC
* colors
* shapes
* finder style
* timing/alignment
* logo
* D25
* Line
* DSJ
* Function
* RandomRectangle
* Bubble
* Image
* Resample
* QZ
* backdrop
* RNG.

### Stale generation mode

`regenerate()` snapshots:

```text
val s = _state.value
```

and later builds the design from current state but obtains:

```text
val mode = s.generationMode
```

from the earlier snapshot.

A rapid state change can therefore give:

```text
current design
+
previous generation mode
```

within one render generation.

**Confidence: CONFIRMED architectural race**

Even though generation counters prevent stale commits, they do not eliminate this internal snapshot inconsistency.

---

## Preview vs export

Preview:

```text
effectiveSize = min(userSize, 512)
```

Export:

```text
effectiveSize = userSize
```

So:

```text
same UI state
→ preview design != export design
```

This is intentional for performance, but it means PREVIEW ≠ EXPORT literally.

The correct parity requirement should instead be:

```text
normalize(preview geometry)
==
normalize(export geometry)
```

for identical style state.

That needs explicit tests.

---

## Rapid controls

The cancellation/generation-token pattern is reasonably strong:

```text
cancel previous
+
generation ID
+
ensureActive()
+
generation comparison before UI commit
```

This is much safer than simply launching a coroutine for every slider movement.

---

## Input payload handling

As noted earlier:

```text
s.content.trim()
```

is a correctness issue.

---

## Export concurrency

The single-flight:

```text
exportJob?.isActive == true
```

is good.

But a stronger state machine would explicitly represent:

```text
Idle
Rendering
Validating
Writing
Completed
Cancelled
Failed
```

instead of many loosely related flags.

# 14. MEMORY / PERFORMANCE / LOW-RAM AUDIT

## 4096² bitmap

A single:

```text
4096 × 4096 × 4
```

ARGB_8888 bitmap is approximately:

```text
67,108,864 bytes ≈ 64 MiB
```

A real export can simultaneously involve:

```text
source bitmap
+
render bitmap
+
temporary scaled/preprocessed bitmap
+
SVG/Base64 buffers
+
PNG byte arrays
+
decoder buffers
```

so peak usage can become much larger than the final image alone.

## Strong positives

VeilFrame already contains:

* 512px interactive preview cap
* streaming animation rendering
* temporary-file APNG/video handling
* bitmap allocation failure handling
* typed export errors
* some explicit recycling.

These are good architectural decisions for 6–16 GB devices.

## High-risk path: animated SVG

`AnimatedQrGenerator.generateAnimatedSvg()` stores each complete frame SVG in a `StringBuilder`.

When each frame includes Base64 images, memory grows approximately with:

```text
frameCount × encodedImageSize
```

This is exactly the sort of workload that can hurt a low-RAM user.

### Safer architecture

For animated SVG:

```text
static SVG structure
+
single image geometry
+
N image href references
+
animation metadata
```

rather than N full SVG documents.

---

## SVG Base64

`SvgExporter.bitmapToBase64()` creates image bytes and Base64 strings.

That creates multiple representations:

```text
Bitmap
→ compressed byte[]
→ Base64 byte/string
→ larger SVG String
```

For large embedded art this is a major transient allocation.

---

## Preview memory

The 512 cap is a good idea.

But preview state still simultaneously retains source/background/logo/result bitmaps.

Bitmaps should have an explicit ownership policy:

```text
UI-owned
source-owned
renderer-owned
export-owned
```

rather than relying on `recycle()` from the ViewModel.

---

## `runBlocking`

`QrGenerator.generateWithResult()` is a synchronous API and invokes scan validation through `runBlocking`.

This is dangerous for arbitrary callers:

```text
Main thread caller
→ generateWithResult()
→ runBlocking
→ decoder
```

The ViewModel mostly protects itself with `Dispatchers.Default`, but the public API remains unsafe.

---

# 15. SCANNABILITY AUDIT

VeilFrame has a substantially better validation architecture than a basic QR renderer.

It checks:

* actual decoder result
* expected payload
* contrast
* finder integrity
* logo overlap
* multiple resolution fallback
* ZXing fallback
* ML Kit primary decoder.

That is good.

### But it does not satisfy the complete requested matrix

The user-requested audit calls for:

```text
multiple scales
Canvas
SVG rasterization
PNG
JPEG
high resolution
low resolution
every style
```

The current validation architecture does not comprehensively execute all of those.

### Major inconsistency

Quiet-zone warning ≠ scan readiness.

This should be corrected.

### Finder verification

The validator samples representative pixels rather than structurally comparing the intended finder geometry to the rendered result.

This can produce false confidence.

### Logo recovery budget

The comments state approximate QR loss capacity of:

```text
L ~7%
M ~15%
Q ~25%
H ~30%
```

but the implementation uses:

```text
L = .05
M = .12
Q = .20
H = .25
```

That is a deliberate conservative budget, not an exact QR theoretical capacity.

It is fine as a safety policy, but should be labeled as:

```text
VeilFrame conservative logo policy
```

rather than implied to be the QR specification itself.

# 16. TEST QUALITY AUDIT

This is one of the most important findings.

## Strong tests

`ResampleImage3x3Test.kt`

is genuinely detailed.

It verifies:

* 3×3 traversal
* center anchors
* functional exclusions
* contrast/exposure
* AspectFit
* padding suppression
* Canvas/SVG coordinate correspondence
* deterministic seeds
* ZXing decode.

That is good engineering.

`JvmCanvasVsSvgDifferentialTest.kt` is also substantially stronger than structural XML tests because it actually rasterizes and compares pixels.

## Weakness: self-oracle problem

Most parity tests compare:

```text
Veil implementation
vs
Veil expectation
```

rather than:

```text
Veil
vs
EFQRCode-generated reference
```

For example:

`VeilQrEncoderParityTest`

tests the expected QR mathematics but doesn't ingest EF's actual output.

`EfQrCodeStyleParityVerificationTest`

checks values such as:

```text
Bubble color = #8ED1FC
DSJ defaults
Function formula
Image mask structure
```

but these are derived assertions, not generated-artifact comparisons.

### Consequence

A systematic porting mistake could pass all those tests if both the implementation and the expected assertions share the same mistake.

## What is missing

There is no permanent golden corpus such as:

```text
EFQRCode 7.0.3
payload
EC
version
style
parameters
EF SVG
EF raster
Veil SVG
Veil raster
pixel diff

```

That is the single biggest test-quality gap.

# 20. FINAL VERDICT

# **PARTIAL PARITY**

VeilFrame is **not** a superficial reimplementation. The QR encoder, matrix model, function classification, shared geometry infrastructure, image preprocessing, 3×3 resampling engine, typed error model, streaming animation work, and scanability infrastructure demonstrate a serious parity effort.

The QR encoding layer is especially strong: the architecture is clearly derived from EFQRCode's `QRCodeSwift`/qrcode.js behavior, including byte mode, version selection, RS coding, BCH, mask selection and matrix construction.

The problem is that **EFQRCode-level parity has not yet been demonstrated at the rendered-artifact level**, and several concrete differences are already proven:

* D25 default quiet-zone mismatch.
* Legacy EC argument ignored.
* SAFE quiet-zone contract mismatch.
* scanability quiet-zone warning does not hard-gate readiness.
* UI trims payload content.
* stochastic style random sequences differ.
* deterministic rendering is not the default for resampling in the UI.
* Canvas and SVG still have independent style paths.
* SVG export is not validated as an SVG artifact.
* animation SVG materializes substantially different structure and can have materially higher memory cost.
* several existing “parity” tests validate VeilFrame against its own assumptions rather than against an actual EFQRCode oracle.

So VeilFrame currently sits in this state:

```text
QR ENCODING              STRONG PARITY
FUNCTION CLASSIFICATION  STRONG PARITY
CANONICAL GEOMETRY       STRONG FOUNDATION
BASIC STYLE              STRONG / NEAR PARITY
FUNCTION STYLE           STRONG ALGORITHMIC PARITY
IMAGE_RESAMPLE CORE      STRONG ALGORITHMIC PARITY
IMAGE_FILL               STRONG STRUCTURAL PARITY

BUBBLE                   PARTIAL
D25                      PARTIAL
DSJ                      PARTIAL–STRONG
IMAGE                    PARTIAL
LINE                     PARTIAL
RANDOM_RECTANGLE         PARTIAL
ANIMATED SVG             PARTIAL

CANVAS ↔ SVG             STRONGER, BUT NOT FULL-SCOPE PROVEN
EF ↔ VEIL PIXEL PARITY   NOT PROVEN
SAFE GENERATION          CONTRACT BUGS
LOW-RAM                  GOOD DIRECTION, IMPORTANT HOTSPOTS
UI INTEGRATION           GOOD FOUNDATION, CORRECTNESS GAPS
```

The most important architectural next step is **not adding more QR styles**. It is establishing a real EFQRCode golden-oracle corpus and making every rendering backend consume one canonical resolved geometry/compositing representation. Once that exists, the remaining mismatches become measurable rather than subjective.
